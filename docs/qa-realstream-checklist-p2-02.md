## 1. 输入前置

执行正式验收前，需具备以下输入：

1. `docs/dev-realstream-report-p2-01.md`
2. DEV 提供的启动参数与最小复现命令
3. 至少 1 条完整流式对话证据（`>=3` 个 `message.delta`）
4. 异常样例证据（超时/子进程失败/鉴权）

## 2. 验收项与判定标准

### 2.1 连续两轮真实回复

1. 在同一会话中连续执行两次 `continue`。
2. 每轮都出现非模板化 assistant 内容（非固定 mock 文案）。
3. 两轮响应内容具备上下文关联或差异，不是重复常量输出。

判定：任一轮缺失真实内容即 `FAIL`。

### 2.2 增量流式可观测

1. 每轮至少观测到 `>=3` 条 `message.delta`。
2. `message.delta` 在时间上分段到达，而非单次打包后一次性返回。
3. 最终存在 `message.done` 收尾。

判定：若仅 `message.done` 或 `delta<3` 即 `FAIL`。

### 2.3 刷新后历史可重建

1. 完成两轮对话后刷新页面。
2. 重新拉取 `events` / WS backlog 后，历史 `user/assistant` 气泡顺序与文本可重建。
3. `seq` 单调递增且无倒序。

判定：消息缺失、顺序错乱或重建失败即 `FAIL`。

### 2.4 子进程异常语义正确

覆盖至少以下异常：

1. 鉴权失败：`4010`
2. 子进程/会话异常：按契约映射为标准业务码并保留 `request_id`
3. 超时场景：返回可识别错误码与可读错误信息

判定：错误码、HTTP 状态、错误体语义任一不符合契约即 `FAIL`。

## 3. 建议执行顺序（正式验收时）

1. 启动服务（使用 DEV 提供参数）。
2. 执行 API 健康与鉴权冒烟。
3. 创建新会话并执行两轮 continue，抓取 events + WS 证据。
4. 页面侧验证气泡流式与刷新重建。
5. 注入异常并核对错误语义。
6. 输出 `docs/qa-realstream-p2-02.md`（逐项 PASS/FAIL + Go/No-Go）。

正式报告文件：`docs/qa-realstream-p2-02.md`

1. 环境与版本（Go/Node/服务参数）

3. 4 项验收逐项结果（含证据路径）
4. 风险说明与最终 `Go/No-Go`
